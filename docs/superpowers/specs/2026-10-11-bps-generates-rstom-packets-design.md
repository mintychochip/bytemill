# BPS generates rstom's packet layer: design (waves 0-1)

**Status:** approved direction (user, 2026-10-11). This spec covers Wave 0 (foundation) and
Wave 1 (first swap). Waves 2-5 are outlined in section 7; each gets its own spec and plan.
**Date:** 2026-10-11

## 1. Goal

The packet layer of `rstom` (the Rust port of Minestom, `/home/jlo/dev/rstom`) is generated by
BPS, so the protocol is described once, in schemas verified against vanilla 26.3, instead of
being ported by hand. **End state:** every payload file under
`crates/rstom/src/network/packet/{client,server}/**`, the package `list()` tables, `ported.rs`
and the `packet_vanilla` id tables are BPS output. Hand-written code remains only for the packet
*machinery* (`packet`, `serializer`, `packet_registry`, `packet_parser`, `packet_reading`,
`packet_writing`, `client_packet`, `server_packet`, `sendable_packet`), for the *domain codecs*
the packets bind to (`ItemStack::network_type()`, `Component`, particles, entity metadata, NBT),
and for behavior helpers on packet types.

### Facts this design rests on (verified 2026-10-11)

- `crates/rstom-packets` (Go `packets_gen`) and `crates/bps_rstom` (BPS) are standalone mirrors.
  Nothing depends on either. The server runs on the hand tree. `rstom` cannot depend on a
  packets crate: its core network types import `coordinate`, `codec`, `nbt`, `registry`, `text`
  and `crypto`. Generated code therefore lives **inside `crates/rstom`**, at the hand tree's paths.
- Consumers of the hand packet types: ~106 `rstom` src files (~911 uses), ~2,257 uses in
  `rstom/tests` (the parity probes build Java-shaped values), ~196 in examples, 2 plugin files.
- Of 240 hand packets, 64 already match the BPS-derived struct field for field (48 identical, 16
  fieldless); 27 more differ only by field names; the rest differ in types (`Component`,
  `ItemStack`, enums, `Pos`) or decomposition (nested records, optionals).
- The hand API is more than field names. `ClientKeepAlivePacket` derives `Copy` and `Eq`, its
  serializer struct is private, and a fieldless packet is a unit struct served by
  `ConstantSerializer`. Docs carry Java provenance.
- A first attempt (`packets_gen`, `a642e9f..933b36c`) generated into the hand tree in one step,
  left `master` red, and was pulled back to a standalone crate. This design is incremental and
  gated per packet.

## 2. Decisions

1. **API preserved.** Generated files keep the type names, module paths, field names and types,
   derives, `new()` signatures, serializer names and visibility, and docs of the hand files.
   Callers (~106 src files) and the parity tests are not edited.
2. **Vanilla wins.** The wire truth is what a vanilla client accepts; vanilla's decompiled codecs
   are the authority and BPS is audited against them. Where Minestom or the hand port differs,
   BPS wins. Fixture cases that pin a Minestom deviation (`delete_chat`,
   `move_minecart_along_track`) are annotated as known Minestom divergences and assert the
   vanilla bytes once those packets swap.
3. **Generate everything.** The end state has no hand-written payload files. Stopping after any
   wave leaves a coherent mixed tree.
4. **Defaults:** schemas, shapes and bindings live in `protoc`; `rstom` commits the generated
   output with a drift check; `bps_rstom`, `rstom-packets` and `packets_gen` are retired at
   cutover; work happens in a worktree.

## 3. Non-goals (waves 0-1)

Host bindings for domain types, field renames, count-field elision, nested records and enums,
generating `ported.rs` / `mod.rs` / id tables, retiring the mirror crates, and any change to
packet machinery or to callers.

## 4. Architecture

```text
protoc                                                    rstom (worktree)
  schemas/minecraft_26_3*.bps    wire layout, vanilla-verified
  targets/rstom/shapes/**.json   the hand API of each swapped packet      bps emit rstom-tree
  rstom tools/packets_gen/...    class table (id -> Minestom class)  --->   crates/rstom/src/network/packet/**   one file per swapped packet
                                                                           crates/rstom/tests/bps_wire_pins.rs     the pin gate
                                                                           crates/rstom/tests/bps/wire_pins.json   pinned bytes, all 260 id-table entries
```

**The shape directory is the migration ledger.** A packet is swapped exactly when it has a shape
file; `emit rstom-tree` generates those packets and leaves the rest alone. Cutover is the day
every packet has one.

### 4.1 Shape file

`targets/rstom/shapes/<group>/<package>/<stem>.json`, mirroring the module path. It is extracted
from the hand file once (`bps shapes extract`) and is the input from then on:

| key | meaning |
|---|---|
| `class`, `module` | Minestom class and module path |
| `module_docs`, `struct.docs`, `fields[].docs`, `new.docs`, `serializer_fn.docs`, `serializer_struct.docs` | doc lines kept from the hand file |
| `struct.derives`, `struct.form` | exact derive list; `braced` or `unit` |
| `fields[]` | `name`, Rust `type`, in wire order |
| `new` | `present`, `must_use`, `const`, `attrs` (other attributes on `new`, verbatim), `body` (non-trivial `new` statements, verbatim; omitted when `new` is only `Self` or `Self { <fields in order> }`) |
| `serializer_struct` | `style` (`struct` or `constant`), `name`, `pub`, `read_via_new` (hand `read` used `Box::new(<Cls>::new(...))`) |
| `extras` | optional sibling `<stem>.ext.rs` holding hand-written `impl` helpers |

Wave 1 requires the BPS-derived field list to equal `fields` (names, order, Rust types); the
emitter errors otherwise. Later waves widen this with bindings and mappings.

### 4.2 Generated file

First line `//! Generated by \`bps emit rust\` ...` (the repo's generated-file marker), then the
module docs from the shape, the struct with the shape's derives and docs, `new()` and
`serializer()` as the shape says, `impl Packet` (`CLASS_NAME`), the marker traits, and the
serializer (`XSerializer` struct or `ConstantSerializer`). `write`/`read` come from the BPS
schema through the existing emitter; when `read_via_new` is set, `read` ends with
`Box::new(<Cls>::new(<field names in wire order>))` after the usual `let` reads. If `extras` is set the file ends with
`#[path = "<stem>.ext.rs"] mod ext;`, `#[allow(unused_imports)] pub use ext::*;` (so a module-level constant keeps its path and an empty ext module does not trip `-D warnings`); the hand `ext` file holds helpers such as
`ClientInputPacket::forward()`. Inline hand tests are not carried over: the pin gate replaces them.

### 4.3 CLI (`protoc`)

```bash
python -m bps.cli shapes extract <schemas> --rstom <workspace> [--eligible | --class <Name> ...] [--out <dir>]  # hand file -> shape json
python -m bps.cli emit rstom-tree <schemas> --rstom <workspace> [--shapes <dir>] [--check]  # shapes -> files, pins
```

`--check` regenerates in memory (with `rustfmt`) and fails on any difference, on a shaped packet
whose file lacks the generated marker, and on a generated file with no shape. Output files are
split to respect the 400-line cap by construction.

## 5. The wire-pin gate

`crates/rstom/tests/bps_wire_pins.rs` reads `tests/bps/wire_pins.json`, generated from the BPS
interpreter's reference bytes (`bps/synth.py`), one row per id-table entry
`{side, state, id, class, hex}` (260 rows). For each row it takes the serializer **from the live
registry** (`packet_vanilla::*_registry()`), so it also checks the id tables, then:

1. the class at that id has the expected simple name;
2. `read` consumes every byte (inside `catch_unwind`);
3. `write` of the decoded value reproduces the pinned bytes.

Before a packet swaps this is the **hand-vs-BPS comparison**; after, the same row pins the
generated serializer to the interpreter. Rows that fail are reported together, not first-fail.
Triaged failures live in `tests/bps/wire_pins_known.json` with a category:

| category | meaning | resolution |
|---|---|---|
| `bps-bug` | BPS layout disagrees with vanilla's source | fix the schema, add a ground-truth test in `protoc` |
| `hand-bug` | the hand port disagrees with vanilla | the swap fixes it |
| `minestom-deviation` | the hand port mirrors a Minestom bug | vanilla wins at the swap; annotate the fixture case |
| `synth-artifact` | the synthetic value is not representable by the hand port | change the synthetic value |
| `domain-limit` | the hand type cannot hold a valid vanilla value | decided per case |

An entry whose row now passes fails the test ("stale"), so the list only shrinks.

## 6. Gates

Every swap is gated by, in order: BPS pins and ground-truth tests (`protoc`);
`tools/check-file-length.sh` (no new violations); `cargo clippy --workspace --all-targets -- -D
warnings`; the packet-related `rstom` tests plus the pin gate; `emit rstom-tree --check`; and an
end-to-end smoke (`tools/e2e_client.py` against `run_server`) at the end of a wave where
resources allow. The full `cargo test -p rstom` runs when disk and CPU allow.

**Environment constraints (observed 2026-10-11).** The machine is shared with a running
benchmark loop (`run_server_wip`, ~770% CPU, load ~11 on 24 cores) and `/home` is 98% full
(13 GB free, `rstom/target` is 546 GB; one `librstom` rlib is ~500 MB with debuginfo). So: every
cargo invocation runs under `nice -n 19 ionice -c3` with `CARGO_BUILD_JOBS=4`, a private
`CARGO_TARGET_DIR` in `/dev/shm`, `CARGO_PROFILE_DEV_DEBUG=0` and `CARGO_INCREMENTAL=0`; nothing
builds on `/home`; the user's `rstom/target` is never used; and `protoc`'s own rstom-compile test
moves off it too.

## 7. Waves

| wave | what BPS learns | ~packets |
|---|---|---|
| 0 | in-tree emitter, shape extractor, pin gate; triage of every hand-vs-BPS difference | none swap |
| 1 | nothing new: shapes already equal | 64 |
| 2 | field renames, count-field elision, type aliases | ~55 |
| 3 | domain bindings: enums, `Component`, `ItemStack`, `Pos`, particles, entity metadata | ~55 |
| 4 | nested records, enums, optionals; flag accessors; extension files | ~60 |
| 5 | `ported.rs`, `mod.rs` and id tables; retire `rstom-packets`, `packets_gen`, `bps_rstom`; update `AGENTS.md`, `PORTING.md`, constraint docs | cutover |

Counts are script-derived and approximate. Wave 4 is where cost jumps; it is re-confirmed with
the user before it starts.

**Frames walkers (waves 2-5):** scan payloads (NBT, slot, id_set, particle, and similar) still
render as `crate::frames::<walker>(...)` in the in-tree emitter, but rstom has no `frames`
module yet. `tree_packet` refuses to emit those packets until a wave spec chooses either
inlining the walker per packet or adding a small private `frames` module under the packet tree.

## 8. Workflow

- `rstom` work is in the worktree `/home/jlo/dev/rstom-bps`, branch `bps-packets`, based on
  `0bbef38` of the autoresearch branch: it carries `docs/constraints/**` (absent on `master`)
  and the `bps_rstom` drop-in commit. That branch is a live optimisation loop whose tip moves, so
  a fixed non-experiment commit is the base. `tokio-perimeter` has an identical packet tree and
  only changes `network/player/**`; no conflicts are expected.
- `protoc` commits go to `master` as before; `rstom` commits go to `bps-packets`, one logical
  step each. Nothing is merged or pushed; the user decides.
- Governance edits in `rstom` (wave 1): `AGENTS.md` (generated-file rule and verification list),
  `PARITY_CONTRACT.md` (vanilla-client compatibility outranks a recorded Minestom deviation),
  `BPS_RSTOM_CRATE.md` (in-tree generated layer), `docs/constraints/INDEX.md`.

## 9. Risks and open items

- Deleting inline hand tests loses assertions beyond round trips. Mitigation: the pin gate runs
  on the same value, and the hand-vs-BPS comparison runs before each swap.
- Performance: generated serializers use the same `NetworkBuffer` calls as the hand ones, but no
  latency benchmark can run while the loop owns the machine. The user measures.
- The comparison may expose many BPS errors; each is fixed with a ground-truth test in `protoc`.
- No real vanilla client is available here; vanilla's decompiled source is the stand-in. The
  user confirms against a real client.
- At cutover the class table (today `packets.json` inside the retired `packets_gen`) moves into
  `protoc`.

## 10. Acceptance

**Wave 0.** `shapes extract` writes a shape for each of the 64 wave-1 candidates into a scratch
directory, and `emit rstom-tree --shapes <scratch>` accepts every one (the BPS-derived fields
equal the shape's `fields`). With the real ledger (`targets/rstom/shapes/`, 64 shapes)
`emit rstom-tree --check` is clean on a worktree that matches the ledger. The pin gate runs over all
260 rows and every non-passing row has a triage entry with a category and reason; each
`bps-bug` is fixed or explicitly deferred.

**Wave 1.** First the 64 shapes move into the ledger. Then every packet with a shape file is
generated at its hand path with the generated marker and no hand serializer code; `git diff`
outside generated files, `*.ext.rs`, the pin gate and governance docs is empty (no caller, test
or plugin edit); the gates in section 6 pass on the worktree; swapped packets have no
`wire_pins_known.json` entry.
